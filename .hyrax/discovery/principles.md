## Non-Obvious Rules

- Proxy management logic is centralized in a singleton `ProxyManager` accessed via `getProxyManager()` rather than each route constructing its own proxy configuration; new server-side code needing a proxy must go through this singleton. (`getProxyManager` — artifacts/api-server/src/routes/utils/proxyManager.js)

## Explicit Conventions

- Legacy/older Facebook-automation routes live under `artifacts/api-server/src/routes/legacy/` as plain JavaScript files (e.g. `artifacts/api-server/src/routes/legacy/bmCreator.js`), while newer routes are written in TypeScript (e.g. `artifacts/api-server/src/routes/permissions.ts`, `artifacts/api-server/src/routes/invite.ts`) — new route work should be added as `.ts` outside the `legacy/` folder rather than as `.js` inside it. (`router` — artifacts/api-server/src/routes/legacy/bmCreator.js)
- Server-side logging goes through the shared pino `logger` exported from `artifacts/api-server/src/lib/logger.ts`, with an `isProduction` flag controlling formatting, instead of using `console.log` in route/service code. (`logger` — artifacts/api-server/src/lib/logger.ts)
- Frontend components that need small utility class-name maps (Tailwind) define a local `C`/`inputCls`/`labelCls`/`panelCls` set of string constants at the top of the modal file (as in `BmCreatorModal.jsx`, `InviterUserModal.jsx`, `CcFromBmModal.jsx`) rather than importing shared style constants from a common module — each modal owns its own styling constants. (`inputCls` — artifacts/vortex/src/components/InviterUserModal.jsx)
- Admin-only route handlers guard access with the shared `requireAdmin` middleware rather than re-implementing role checks per route (e.g. used in `artifacts/api-server/src/routes/legacy/adminRoutes.js`). (`requireAdmin` — artifacts/api-server/src/middlewares/requireAdmin.js)

## Architecture Decisions

- Route modules define an Express Router and are mounted centrally rather than attaching routes directly to the app; each route file exports a `router` object (e.g. `artifacts/api-server/src/routes/health.ts`, `artifacts/api-server/src/routes/index.ts`) which is composed together instead of defining routes inline in `app.ts`. (`router` — artifacts/api-server/src/routes/index.ts)
- The generated API client's fetch wrapper (`lib/api-client-react/src/custom-fetch.ts`) uses a module-level `_baseUrl`/`_authTokenGetter` set via `setBaseUrl`/`setAuthTokenGetter`, rather than axios instances, for configuring the generated orval client — treat this file as the integration point for base URL/auth wiring instead of adding axios interceptors. (`setAuthTokenGetter` — lib/api-client-react/src/custom-fetch.ts)
- API client and Zod schema code in lib/api-client-react and lib/api-zod is generated by orval from the spec in lib/api-spec (see `lib/api-spec/orval.config.ts` exporting `root`, `apiClientReactSrc`, `apiZodSrc`) and must not be hand-edited; regenerate via orval config changes instead. (`apiClientReactSrc` — lib/api-spec/orval.config.ts)
